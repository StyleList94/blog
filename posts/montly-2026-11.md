## 이달의 표지

Deno 팀이 런타임을 내려놓았다

[Deno 팀이 Cloudflare에 합류한다](https://deno.com/blog/cloudflare). 여기까지만 들으면 흔한 인수 소식이다. 문제는 그다음 문장이다. **Deno를 계속 만들려고 가는 게 아니다.** 9월호 관망에 올렸던 celld, 그러니까 S3 버킷 하나로 조율하는 셀프호스팅 Durable Objects를 Cloudflare의 workerd에 통합하는 게 이 팀의 새 일이다.

남는 쪽의 일정은 이렇다.

- **Deno 런타임**: 앞으로 1년간 공식 수정만 받는다.
- **Deno Deploy**: 6개월 뒤 종료된다.
- **JSR**: Cloudflare 인프라로 옮긴다.

타이밍도 묘했다. 발표 며칠 전 2021년에 Deno를 반겼던 개발자가 [Deno에서 Node로 돌아온 이야기](https://dbushell.com/2026/10/03/deno-to-node/)를 올렸다. 사이트 생성기를 거의 손대지 않고 그대로 옮길 수 있었다는 대목이 이번 소식과 겹쳐 읽힌다.

반응은 둘로 갈렸다. 한쪽은 추모다. [Deno의 실망스러운 죽음](https://brettcodes.com/the-disappointing-death-of-deno/)이라는 제목이 그대로 정서를 말해준다. 다른 쪽은 감사다. vlt의 Darcy Clarke는 [Deno 고맙다, 경쟁이 JavaScript를 움직인다](https://www.vlt.io/blog/competition-keeps-javascript-moving)에서 Deno와 Bun이 압박한 덕에 Node와 npm이 좋은 아이디어를 받아들였고 생태계 전체가 나아졌다고 정리했다.

> **Deno는 Node를 이기지 못했지만 Node를 바꿨다.**

그리고 경고가 있다. RedMonk 분석가는 [JavaScript 런타임 단일 문화](https://redmonk.com/kholterhoff/2026/10/27/js-runtime-monoculture/)를 우려한다. Deno가 정리 수순에 들어가면 서버 런타임 선택지는 Node, Bun, workerd로 좁아진다. IE6 시절, Chromium 독주, io.js 포크까지 꺼내며 경쟁자가 줄어들 때 무슨 일이 생겼는지 상기시킨다.

이야기는 아직 안 끝났다. 월말에 Deno 팀의 Bartek Iwańczuk가 Deno를 재단으로 옮기는 작업을 하고 있다고 밝혔다. 새 포크 Ende도 나왔는데 Node 호환성을 버리고 샌드박싱에 집중하겠다고 한다. Deno 2.9.8도 나왔다.

**Deno Deploy에 뭔가 올려 둔 팀은 6개월 시계가 이미 돌고 있다.** JSR에 패키지를 퍼블리시하거나 CI 스크립트를 Deno로 돌리고 있다면 이번 분기 안에 이전 계획을 잡아 두는 게 맞다. 갈 곳은 대부분 Node일 텐데, Node 26이 10월 말 LTS가 됐으니 시점은 나쁘지 않다.

## 즉시

이번 주 안에 끝내라. 미루면 그게 사고다

### Next.js

추천 기본값에서 터진 RCE

10월 14일, [정기 일정 밖에서 보안 업데이트가 나왔다](https://nextjs.org/blog/nextjs-security-update-october-14-2026). Critical RCE 2건과 High DoS 1건이다. 이 중 2건은 업스트림과 조율하느라 9월 보안 릴리스에서 밀린 것들이다. **공개 PoC가 이미 돌고 있다.**

```bash
npm install next@16.4.1   # Active LTS
npm install next@15.5.28  # Maintenance LTS
```

**① `use cache` RCE** (GHSA-673q-mjm6-r5xr). App Router + Cache Components 환경에서 `use cache` 함수가 typed array 여러 개를 반환하면 인증 없이 원격 코드 실행이 된다. 뿌리는 React Server Components 쪽 버그이고 React 어드바이저리는 GHSA-xqc2-xf4c-x3h3다. **우회책이 없다.** 해당 함수를 안 쓰는 앱도 올리라고 권고한다. Next.js 밖에서 RSC를 쓰고 있다면 `react-server-dom-*`를 19.3.1(또는 19.2.9 / 19.1.10 / 19.0.9)로 올려야 한다.

여기서 웃기 힘든 대목이 있다. 아래 검토에서 다룰 Next.js 16.4는 Cache Components를 모든 앱에 추천하는 기본값으로 올린 릴리스다. **그 16.4의 바로 다음 패치가 Cache Components의 `use cache` RCE 수정이었다.**

**② 이미지 최적화 SVG RCE** (CVE-2026-96889 / GHSA-2464-fhr4-w9xw). Image Optimization API가 SVG를 처리할 때 상위 라이브러리의 메모리 취약점으로 glibc 기반 Linux에서 인증 없는 RCE가 가능하다. 우회책은 Next.js가 쓰는 `sharp`를 0.35.5 이상으로 맞추는 것이다. Alpine(musl) 컨테이너는 영향 범위가 다를 수 있지만 그래도 올리는 게 안전하다.

**③ Server Action DoS** (GHSA-p3m5-59mp-jv5r, High). Server Action이 하나라도 있는 App Router 앱에 조작된 요청을 보내면 CPU를 붙잡아 같은 프로세스의 다른 요청이 막힌다. Pages Router만 쓰거나 Server Action이 없으면 영향 없다.

순서는 셋이다. next 버전을 올리고 lockfile에서 `sharp` 버전을 확인하고 배포 후 `use cache`와 Server Action 사용처를 훑는다. 호스팅 플랫폼이 WAF 규칙으로 일부를 막아 준다 해도 근본 해결은 업그레이드뿐이다.

### Node

fetch 응답만 받아도 걸리는 RCE

10월 21일 [22.x, 24.x, 26.x 전 라인에 보안 릴리스가 나갔다](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases). CVE 10건이고 헤드라인은 번들된 Brotli 디코더의 범위 밖 쓰기(CVE-2026-111497, High)다. 별명은 Node2Shell.

발동 경로가 문제다. `node:zlib`로 직접 압축을 풀 때만이 아니라 **`fetch()`가 Brotli 응답을 자동으로 풀 때도 터진다.** 외부 API를 부르는 BFF, 업로드를 받는 서버, SSR 중에 남의 응답을 가져오는 코드가 전부 해당된다. 잘못된 block switch를 포맷 오류로 끊지 않고 입력 부족으로 처리해 바이트를 계속 이어 붙이다가 8바이트 버퍼를 넘어가는 구조다.

```text
# 수정 버전
v26.12.1 / v24.22.1 / v22.23.4
```

같은 릴리스에 High가 셋 더 있다. 선행 0이 붙은 IPv4(CVE-2026-106069)와 전각 숫자 IP(CVE-2026-105483)로 TLS 호스트명 검증을 우회하는 버그, `dns.resolve*()`와 `dns.reverse()`가 NUL 문자에서 잘리는 버그(CVE-2026-105482)다. Medium 중에는 `randomUUID`와 `randomInt`의 엔트로피 캐시가 startup snapshot과 SEA에 저장돼 실행할 때마다 값이 반복되는 문제가 눈에 띈다. 단일 실행 파일로 배포하는 CLI라면 그냥 넘길 게 아니다.

현황을 정리하면 이렇다. 공개 PoC는 일부러 약화한 테스트 빌드에서만 코드 실행에 성공했고 표준 빌드에서는 크래시와 제한적인 메모리 읽기까지만 보고됐다. 그런데 이후 ELLIO가 [실제 악용 트래픽을 보고했다](https://thehackernews.com/2026/10/researchers-demonstrate-node2shell-rce.html). Vercel 방화벽 규칙은 서버가 밖에서 가져오는 Brotli 응답까지는 막지 못한다. **우회 수단이 없으니 업그레이드가 유일한 답이다.**

두 가지를 더 기억해라. Node 20 이하는 EOL이라 패치 자체가 없다. 그리고 결함은 Google의 Brotli 라이브러리에 있으니 Node 말고 Brotli를 번들한 다른 소프트웨어도 점검 대상이다(Brotli 1.2.1 / 1.1.1 / 1.0.10에 같은 수정이 들어갔다).

### 나머지 둘

한 줄씩 끝나는 것들

- [**Handlebars 4.7.10**](https://github.com/handlebars-lang/handlebars.js/releases/tag/v4.7.10): CVE-2026-106446, CVSS 9.8. 4.0.0부터 4.7.9까지가 대상이다. `compile()`이나 `precompile()`에 문자열 대신 미리 파싱된 AST 객체를 넘기면 일부 노드만 검증하는 틈으로 JavaScript를 심을 수 있다. 4.7.9에서 막았던 CVE-2026-33937 방어까지 우회된다. **템플릿을 문자열로만 넘기는 앱은 영향이 없다.** 다만 사전 컴파일 캐시처럼 AST를 직접 다루는 플러그인이나 프레임워크 레이어를 거쳐 간접적으로 걸릴 수 있으니 의존성 체인을 함께 봐라.
- [**Express 5.3.0**](https://github.com/expressjs/express/releases/tag/v5.3.0): `qs`, `proxy-addr`, `body-parser` 의존성 패치로 CVE 5건을 해결했다. 월말에는 [body-parser 버그가 따로 공개됐다](https://expressjs.com/en/blog/2026-10-28-cve-2026-111181/). gzip 본문 뒤에 바이트를 덧붙인 요청 하나로 프로세스가 죽는다. body-parser 2.4.0과 1.20.9에서 고쳐졌다.

### Next.js 16.4

Cache Components가 추천 기본값이 됐다

[16.4부터 Cache Components가 모든 앱에 추천하는 모델이 됐다](https://nextjs.org/blog/next-16-4). `create-next-app`으로 만드는 새 프로젝트는 기본으로 켜져 있고 Next.js 17에서는 정식 기본값이 될 예정이다. 기존 앱은 `next upgrade --agent`와 전용 Skill로 에이전트에게 마이그레이션을 맡길 수 있다.

```ts
// next.config.ts
export default {
  cacheComponents: true,
  partialPrefetching: true,
};
```

새로 생긴 것 중 실무에서 바로 쓸 만한 건 둘이다. `ensureStatic` 라우트 세그먼트 옵션은 특정 라우트나 레이아웃이 항상 정적이도록 강제한다(`'navigation' | 'prefetch' | 'shell'` 단계별). **마케팅 페이지나 상품 상세처럼 완전 정적이어야 하는 곳에 동적 컴포넌트가 실수로 섞이면 빌드 단계에서 막힌다.** 그리고 `next/cache`의 `navigation()`과 `prefetch()`로 prefetch 때 무엇을 미리 가져올지 세밀하게 정할 수 있다. Vercel은 v0 앱 빌더에 이 조합을 적용해 [로딩 스켈레톤을 줄인 사례](https://nextjs.org/blog/improving-navigation-experience-in-v0-with-nextjs-16-4)도 공개했다.

공짜로 얻는 것도 있다. Turbopack 메모리 할당 개선으로 메모리 사용량 30%, 컴파일 시간 15%가 줄었고 Rust 기반 React Compiler는 최적화가 필요 없는 파일을 건너뛰는 fast check가 생겼다.

**조건 셋.** 위 즉시 섹션의 RCE 때문에 16.4.0은 건너뛰고 16.4.1부터 시작해야 한다. Cache Components는 아직 추천 단계이고 레거시 캐싱 모델과 동작이 달라 옮길 때 캐시 동작을 다시 검증해야 한다. `turbopackGc`, `turbopackLazyDynamicImports` 같은 신규 옵션 일부는 experimental이고 worker threads 옵션은 Node 24.13.1 이상에서 알려진 Node 버그 때문에 child process로 돌아간다.

### TanStack Start 1.0

RSC는 옵션이라고 선을 그었다

1년간 RC였던 [TanStack Start가 1.0이 됐다](https://tanstack.com/blog/tanstack-start-1-0). API 안정성을 공식으로 약속하는 릴리스다.

철학이 분명하다. Next.js처럼 RSC를 프레임워크 중심에 두지 않고 익숙한 클라이언트 모델(클라이언트 내비게이션, 데이터 캐싱)을 유지한 채 SSR과 스트리밍과 서버 함수를 필요한 만큼 얹는다. Tanner Linsley는 RSC를 React 프레임워크로 인정받으려고 채워야 했던 체크 항목이라고 솔직하게 말했고 **tanstack.com 자체도 RSC를 더 이상 쓰지 않는다.**

- **Selective SSR**: 라우트마다 서버 렌더, 서버에서 데이터만 로드, 클라이언트 렌더 중에 고른다.
- **`createServerFn`**: loader나 이벤트 핸들러에서 부르는 타입 안전 서버 함수. 클라이언트와 서버 양쪽을 감싸는 미들웨어가 타입 컨텍스트를 그대로 넘긴다.
- **`createIsomorphicFn`**: 서버 구현과 클라이언트 구현을 나란히 정의하면 빌드가 안 쓰는 쪽을 번들에서 지운다.
- **배포**: 자체 어댑터를 버리고 Vite + Nitro에 맡겼다. Cloudflare Workers, Netlify, Vercel, Render, Railway 경로가 있고 Solid와 Rsbuild도 지원한다.

팀 자체 벤치마크로 SSR 처리량이 약 5.5배 늘었고 [같은 앱을 Next.js 16.4와 비교한 서드파티 측정](https://www.fabwaseem.com/blog/tanstack-start-vs-nextjs)에서는 동적 요청을 2.9\~8.6배 더 처리했다. [Next.js에서 옮기는 공식 가이드](https://tanstack.com/start/latest/docs/framework/react/migrate-from-next-js)도 함께 나왔다.

**Next.js의 RSC와 캐시 복잡도에 지친 팀이라면 작은 라우트 하나로 PoC를 해볼 시점이다.** TanStack Query를 이미 쓰고 있으면 prefetch, 캐싱, 하이드레이션이 깊게 맞물려 더 매끄럽다. 단 벤치마크는 팀이나 개인 측정이니 자기 앱에서 다시 재야 하고 서드파티 플러그인과 호스팅 가이드 생태계가 Next.js만큼 두꺼운지는 따로 확인해야 한다.

### bun check

tsc 없이 tsc 결과를 낸다

[Bun 1.4.3에 내장 타입 체커가 들어왔다](https://bun.com/blog/bun-v1.4.3). Microsoft의 Go 버전 TypeScript를 포팅한 것이고 `tsconfig.json`을 그대로 읽어 tsc와 같은 에러를 낸다. `typescript` 패키지를 설치할 필요가 없다.

호환성 주장이 구체적이다. TypeScript 7.0.2 conformance 테스트 51,210개를 전부 통과했고 일부러 설정을 꼬아 놓은 오픈소스 72개 프로젝트의 1,103개 설정 중 1,102개가 tsc와 같은 출력을 냈다(유일한 불일치는 vuejs/core). 16코어 Apple Silicon 기준으로 VS Code `src`는 1.24초 대 5.98초, Next.js `packages/next`는 0.28초 대 1.82초다. **3\~6.4배 빠르고 메모리는 2.2\~4.9배 적게 쓴다.**

```bash
bun check                # 타입 체크만
bun run --check app.ts   # 실행 전 체크
bun test --check         # 테스트 전 체크
bun build --check        # 빌드 전 체크
```

CI의 `tsc --noEmit` 자리에 넣으면 대형 모노레포에서 체감이 바로 온다. 같은 릴리스에서 유휴 서버 CPU도 1.4.2 대비 67\~89% 줄었다(1초마다 깨우던 GC 타이머를 고쳤다). 1.4.4에서는 Prettier와 oxfmt 설정을 그대로 읽는 `bun fmt`도 들어왔다.

**한계 둘.** JS나 d.ts를 내보내지 않고 언어 서버도 아니다. 에디터 타입 체크는 여전히 기존 TS 서버 몫이다. 그리고 100% 호환은 아니니 CI에 붙일 때는 한동안 기존 tsc 결과와 나란히 돌려 비교해라.

### TypeScript 7.1 Beta

Go로 옮기며 잃은 것을 돌려받는다

[TypeScript 7.1 베타](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)의 핵심은 둘이다. 7.0이 Go로 재작성되면서 사라졌던 JS 컴파일러 API를 대신할 **프로그래밍 API**, 그리고 Vue·Svelte·Astro·MDX 같은 파일 속 코드를 tsc가 직접 검사하게 해 주는 **content mappers**. 속도도 올랐다. MUI 문서 타입 체크가 1.9배 빨라졌고 메모리는 절반만 쓴다.

API는 `typescript/sync`, `typescript/async`, `typescript/fs`, `typescript/ast`로 나뉜다. Go 쪽 메모리를 쓰기 때문에 `using` 선언이나 `close()`/`dispose()`로 명시적으로 해제해야 하고 `snapshot.update()`로 바뀐 부분만 갱신한다. content mappers는 tsconfig의 `contentMappers`로 등록하고 tsc에 `--runExternalCode`를 줘야 동작한다. CSS Modules와 `.graphql`에 적용한 Jovi De Croock의 글도 나왔고 Zod 제작자가 만든 [Reylo](https://reylo.dev/)는 이 기능에 기대어 `.sql` 파일을 import하면 행과 파라미터 타입을 추론해 준다.

그 밖에 `import source x from "./x.wasm"`이 `WebAssembly.Module`을 돌려주고 `--target es2026`이 `Math.sumPrecise`, `Error.isError`, `Array.fromAsync`를 안정 lib에 넣는다.

**지금 할 일은 브랜치 하나다.** `typescript@beta`로 모노레포 전체에 `tsc --noEmit`을 돌려 분배 조건부 타입과 DOM 타입 오류부터 확인하고 SFC를 쓰면 프로젝트 하나에서만 매퍼를 시험해라. RC는 베타 약 한 달 뒤로 잡혀 있다. 함정은 아래 손대지 말 것에 모아 뒀다.

### Node 26 LTS

프로덕션 타깃이 바뀌었다

10월 28일 [26.13.0과 함께 Node 26이 Active LTS(코드명 Lithium)가 됐다](https://nodejs.org/en/blog/release/v26.13.0). 2029년 4월 말까지 업데이트를 받는다. Node 24는 maintenance로 넘어갔고 Node 27 첫 alpha도 예고됐다. 연 1회 릴리스 체계의 첫 사례다.

26.13.0 자체는 26.12.1과 메타데이터 말고는 변경이 없다. 그러니 **보안 수정이 들어간 26.12.1 이상이라는 조건이 자동으로 충족된다.** 10월 중 26 라인에 쌓인 것들은 이렇다.

- **26.11**: 무한 루프 중에도 프로세스를 강제 종료하는 `--process-timeout`, `node:sqlite`의 virtual table, `Buffer.stringLength()`, Alpine x64의 tier 2 승격. 같이 선보인 새 문서 디자인은 HTML 렌더링 버그로 26.11.1에서 롤백됐다.
- **26.12**: 런타임·테스트·watch·permission 설정을 담는 config 파일이 stable로 승격됐고 대부분의 ES 모듈을 동기적으로 로드하게 됐다. top-level await나 로더 훅이 있을 때만 비동기 경로를 탄다.
- **24.22 (LTS)**: 10월호에서 26.10 전용이라 기다리라고 했던 `util.debounce()`와 `util.throttle()`이 24 라인에도 들어왔다.

Docker 베이스 이미지와 CI 매트릭스를 26으로 옮길 때 하나만 확인해라. Linux 공식 바이너리는 Node 25부터 libatomic에 링크되므로 배포판에 따라 별도 설치가 필요할 수 있다.

### MSW 3.0

ESM 전용이 되면서 반으로 줄었다

[API 모킹 라이브러리 MSW가 3.0을 냈다](https://mswjs.io/blog/introducing-msw-3.0). tarball이 416KB에서 234KB로, 타입 정의가 190KB에서 90KB로 줄었다. `graphql`, `path-to-regexp`, `picocolors` 같은 의존성이 빠지거나 선택 peer dependency가 됐다.

- **세분화된 진입점**: `msw/http`, `msw/graphql`, `msw/sse`, `msw/ws`. 루트 `msw` import는 당장 동작하지만 다음 메이저에서 정리되니 지금 옮겨 두는 게 낫다.
- **GraphQL subscription**: `api.subscription()`으로 핸들러를 만들고 `subscription.publish()`로 클라이언트에 데이터를 민다.
- **Node 인터셉션 방식 변경**: fetch나 Node 내부를 패치하는 대신 TCP/TLS 소켓 레벨에서 가로챈다.
- **`defineNetwork`**: 네트워크 소스와 요청 핸들러를 분리하는 실험 API. 장기적으로 `setupServer`/`setupWorker`를 대체할 예정이니 새 테스트 셋업을 짤 때 방향을 염두에 둬라.

**ESM 전용이고 Node 18/20 지원이 끝났다.** Jest의 CJS 기본 설정 위에서 MSW를 쓰고 있다면 3.0 전에 ESM 전환이 먼저다.

### React Router 8.5

자체 View Transition API에 은퇴 예고

[8.5에서 React Router 자체 view transition API가 deprecated됐다](https://reactrouter.com/changelog#v850). 대상은 `viewTransition` props와 옵션, `useViewTransitionState`, `NavLink`의 `isTransitioning` render prop과 `transitioning` 클래스다. v8 내내 동작하고 v9에서 제거된다. 대체재는 10월호에서 다룬 React 19.3의 `<ViewTransition>`이다.

마이그레이션 시작점은 간단하다. 지속되는 레이아웃에서 `<Outlet>`을 `<ViewTransition>`으로 감싸고 기존 props와 상태 기반 스타일링을 걷어낸다. React 19.3 이상이 필요하고 라우터에 `useTransitions={false}`를 걸어 두면 동작하지 않는다.

함께 들어온 unstable API-only 모드(`ssr: "unstable_api-only"`)는 정적 HTML은 CDN에서 서빙하고 loader, action, 재검증, lazy route discovery만 런타임 서버가 맡는 구조다. 다른 origin을 쓰면 `unstable_apiServerOrigin`, CORS, `allowedActionOrigins` 설정이 필요하고 RSC Framework Mode에서는 거부된다. **정적 호스팅과 API 서버를 따로 두는 팀이라면 눈여겨볼 만하지만 이름 그대로 unstable이다.**

### 그 외 넷

라이브러리 둘, 서버 레이어 하나, 공급망 하나

- [**Effect 4.0**](https://effect.website/blog/releases/effect/40): 리소스 관리, 동시성, 재시도, 타입드 에러를 다루는 라이브러리가 코어를 처음부터 다시 만들어 런타임 의존성 0개 단일 패키지가 됐다. 최소 번들 35.6KB에서 7.1KB(5배), 동시 작업 처리량 초당 71만 건에서 457만 건(6.4배), fiber 5만 개 기준 메모리 157.5MB에서 21.8MB(86% 감소). 4.x는 2029년 9월까지 버그 수정, 2030년 9월까지 보안 패치가 보장된다. 공식 글에 브레이킹 목록이 상세하지 않으니 마이그레이션 가이드를 따로 봐라.
- [**Preact 11**](https://preactjs.com/blog/preact-11/): 작업 시작 6년 만에 나온 메이저. Hydration 2.0, 기본 활성 자동 ref forwarding, ESM 전용 패키징, `Object.is` 기반 hooks 인자 비교. `@preact/signals`, `preact-iso`, `@preact/preset-vite` 같은 1st-party 패키지는 이미 호환을 맞췄다. `preact/compat`으로 React 코드를 돌리는 위젯이나 임베드라면 업그레이드 가이드를 따라 검토할 만하다.
- [**H3 v2**](https://h3.dev/blog/v2): Nitro와 Nuxt 서버 레이어를 받치는 HTTP 프레임워크가 표준 Request/Response 위로 전면 재작성됐다. 같은 앱이 Node, Bun, Deno, Workers, 브라우저에서 돈다. 라우팅은 rou3 v1, 미들웨어는 `(event, next)` 패턴이다. Node 20.19 이상이 필요하고 후행 슬래시 처리 같은 라우팅 차이가 v1 동작을 바꿀 수 있다.
- [**GitHub Actions workflow lockfiles**](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available): 정식 출시. 참여한 워크플로에서 액션과 그 의존성까지 고정할 수 있다. 액션 쪽 변경이 CI로 몰래 끼어드는 경로를 막는 장치라 **켜지 않을 이유를 찾기가 더 어렵다.**

## 관망

지금 쓰면 안 되지만 6개월 뒤에 "그거 왜 몰랐지" 소리 안 들으려면

**TSRS와 ts-rust**: TypeScript 7이 Go로 나온 지 얼마 안 돼 Rust 포트가 둘 나왔다. [ts-rust](https://github.com/pingdotgg/ts-rust)는 Theo Browne의 실험이다. 1단계에서 OpenAI 계열 모델로 5개월간 약 40만 달러어치 토큰을 썼지만 호환성 84%에서 멈췄고 2단계에서 Claude Opus 5.5가 처음부터 다시 써서 2주, 약 2만 4천 달러로 목표에 닿았다. 포팅된 Go 테스트 181,711개를 통과한다고 하고 **작성자는 코드를 한 줄도 읽어 본 적이 없다고 직접 밝혔다.** T3 Code 기준 타입 체크는 tsc-rs 7.25초, tsc 7 16.10초다. 그런데 같은 작성자 측정에서 실제 앱 6종 기하평균으로 tsc 7 대비 tsc-rs는 1.61배, bun check(canary 빌드)는 2.95배였다. 40만 달러를 태운 Rust 포트보다 Bun의 Go 포트가 빨랐던 셈이다.

다른 하나인 [TSRS](https://blog.cloudflare.com/typescript-rust-port/)는 Cloudflare, VoidZero, Owner.com의 Max Schwenk가 만들었다. 포크 대신 TypeScript 팀의 설계 결정을 그대로 따르는 포트이고 Oxc 툴체인에서 인큐베이팅한다. 같은 워커 수 기준 TS 7.0보다 최대 8배 빠르고 메모리는 약 70% 적게 쓴다고 주장한다. Go를 Wasm으로 컴파일하면 GC까지 실어야 하지만 Rust는 그럴 필요가 없어 `@tsrs/wasm`으로 브라우저와 임베디드 환경까지 노린다. Owner.com 사내 타입체크가 80초에서 7초로 줄었다. TS 7.1 베타 속도 개선 일부는 tsrs에서 업스트림으로 돌려보낸 것이라고 한다. **두 포트는 하나로 합쳐 LSP까지 지원할 계획이다.** 둘 다 진단 출력 순서가 업스트림과 다르고 ts-rust는 `tsc -b --watch` 멈춤과 장시간 메모리 누수가 보고됐으며 Linux x64와 macOS arm64만 된다. 지금은 CI 별도 잡에서 tsc와 나란히 돌려 숫자만 재 보는 정도가 맞다.

[**TanStack Redact**](https://tanstack.com/redact): 지난 호 관망의 그 런타임이 숫자를 들고 왔다. 빌드 플러그인 하나로 컴포넌트, 훅, import는 그대로 둔 채 브라우저의 React와 React DOM을 작은 재구현으로 바꾼다. gzip 기준 클라이언트 JS+CSS가 Vite 69KB에서 13\~21KB(-70.5%), Start 110KB에서 60\~63KB(-43%), Vinext 139KB에서 99KB, Next.js 176KB에서 140KB로 준다. Next.js와 Vinext에서는 서버 렌더링과 Server Components와 캐싱을 프레임워크가 계속 맡는다. **렌더링은 동기식뿐이라 time slicing과 중단 가능한 렌더링이 없다.** API 차이 목록 없이 호환성 문서만 가리키고 주간 다운로드 약 9,700건에 스타 480개 수준이다.

[**TanStack AI 1.0**](https://tanstack.com/blog/tanstack-ai-1-0): 프레임워크에 묶이지 않는 AI 툴킷이 1.0이 됐다. 채팅, 툴, 미디어 API가 안정화됐고 provider 어댑터가 23개다. 장시간 세션용 에이전트 하네스도 들어왔지만 그쪽 API는 아직 실험 단계다.

[**Remix 3.0**](https://github.com/remix-run/remix/releases/tag/remix%403.0.0): 10월호 관망의 RC가 정식이 됐고 월말에는 3.1까지 나왔다. 공식 발표 글은 아직 없고 React 없이 도는 독립 풀스택 프레임워크라는 점도 그대로다. [v3로 6개월을 일해 본 Sergio Xalambrí의 회고](https://sergiodxa.com/articles/the-remix-way)가 써 보기 전에 읽기 좋은 자료다.

OpenTelemetry는 조금 더 풀어야겠다. [3.x 마이그레이션 가이드](https://github.com/open-telemetry/opentelemetry-js/blob/main/doc/3.x/migration-guide.md)가 길고 조용히 깨지는 곳이 있다.

`sdk-trace-base`, `sdk-trace-node`, `sdk-trace-web`이 `@opentelemetry/sdk-trace` 하나로 합쳐졌고 `BasicTracerProvider`는 `TracerProvider`가 됐다. `OTEL_TRACES_SAMPLER`나 `OTEL_BSP_*` 같은 환경변수 폴백 읽기가 사라졌으니 **환경변수로 샘플링을 조절하던 서비스는 업그레이드 후 설정이 그냥 무시된다.** `NodeTracerProvider#register()`도 없어져 tracer provider, 컨텍스트 매니저, propagator를 직접 등록해야 한다.

번들러 쪽이 더 미묘하다. browser 필드 대신 `#platform` imports와 `node` 조건을 쓰므로, esbuild `platform: neutral`이나 Rollup 기본 `exportConditions`처럼 `node` 조건이 빠진 빌드는 Node에서 브라우저 구현을 집어 들 수 있다. Jaeger propagator 교체는 서비스 전체가 동시에 해야 하니 전환기에는 `CompositePropagator`를 써라. 가이드 본문에도 오타와 잘린 문장이 있어서 예시 코드는 실제 패키지 export와 대조한 뒤 옮기는 게 안전하다.

## 참고

당장 코드를 바꾸진 않지만 다음 분기 의사결정에 쓰일 것들

### 성능 실화 넷

- [Owner, React를 필요한 곳에만](https://building.owner.com/project-speed): 레스토랑 사이트 1만 개 이상을 Next.js에서 Astro + Cloudflare Workers로 옮겨 메뉴 페이지 p75 LCP를 5.4초에서 0.7초로 줄였다. 모바일 Lighthouse는 44에서 90\~99. 주문 플로우 전체를 React island 하나로 두고 `client:load`로 하이드레이션하며 마케팅 페이지는 JS가 거의 없다. 캐시는 게이트웨이 Worker → Workers Cache → R2 → 미스 시 Astro 렌더 순서이고 데이터가 바뀌면 백엔드가 재검증을 밀어 준다. 겪은 문제도 정직하게 적었다. feature flag 하나마다 캐시 변형이 두 배가 되는 variant explosion, SSR에서 React가 두 벌 로드되는 문제(심링크로 단일화). 롤아웃은 PostHog 50/50 실험과 8 → 800 → 4,800 → 전체 단계 배포에 kill switch를 붙였는데 **이 롤아웃 방식 자체가 결과보다 더 베껴 갈 만하다.** 월 8천\~1만 달러 인프라 절감, 식당당 매출 +4% 같은 비즈니스 수치는 전부 자체 데이터다.
- [Booking.com, 최대 Node 서비스 비용 38% 절감](https://medium.com/booking-com-development/node-js-at-scale-rebalanced-how-we-cut-cost-by-38-62ce247a3002): 가장 큰 React SSR 서비스를 pm2 프로세스 클러스터에서 Platformatic Watt의 워커 스레드 구조로 옮기고 로드 밸런싱과 V8 GC까지 튜닝했다. 관련해서 [바쁜 머신에서의 스레드 풀](https://blog.platformatic.dev/more-threads-on-an-already-busy-machine)은 CPU 코어 수만 보고 스레드 풀 크기를 정하면 같은 머신의 다른 프로세스 때문에 역효과가 난다고 짚는다.
- [Trigger.dev, Zod 4로 CPU 3분의 1 감소](https://trigger.dev/blog/zod-4-got-rid-of-a-bunch-of-cpus-for-us): 태스크 페이로드, 배치, 큐 메시지 같은 핫패스에서 Zod를 쓰는 서비스가 3에서 4.5로 올리자 24시간 평균 엔진 워커 CPU 31%, 배치 워커 15%, API 10%가 줄었다. 태스크 트리거 p99는 18% 단축. 파싱 시간이 줄면서 이벤트 루프를 막는 시간도 같이 줄어든 게 원인이다. **사고담이 더 값지다.** 배포 후 누군가 core 패키지에 순수 `zod` import를 추가했고 Zod v3에 머물러 있던 npm 사용자들의 warm start가 느려졌다. 이후 `zod/v4`로 경로를 명시하고 재발 방지 oxlint 규칙을 붙였다.
- [Recraft, 9MB Wasm을 일찍 불러 에디터 17% 개선](https://bra31k.dev/en/blog/same-bytes-17-percent-faster): 바이트는 그대로인데 빨라졌다. Suspense로 컴포넌트가 중단되면서 모듈 다운로드가 React 트리 순서를 기다리고 있었고 다운로드 시작을 트리 밖으로 앞당기자 17%가 나왔다. 무거운 Wasm이나 lazy 모듈을 Suspense 경계 안에서 여는 화면이라면 바로 의심해 볼 패턴이다.

### 덜 하는 쪽이 이긴다

- [죽은 코드는 존재하면 안 된다](https://tkdodo.eu/blog/dead-code-shouldnt-exist): TkDodo가 Sentry에서 Knip으로 미사용 코드 2.8만 줄을 걷어낸 발표의 슬라이드와 대본. 안 쓰는 코드가 생각보다 비싼 이유를 정리했다.
- [빠름은 디자인 결정이다](https://shannadige.com/blog/performance-is-design/): 사이트 만드는 비용은 싸졌지만 결과물은 빠른 노트북과 데워진 캐시 기준으로만 괜찮아 보인다는 글. 저속 폰 시뮬레이션 실측이 구체적이다. 모든 파일이 `max-age=0`으로 나가 페이지뷰마다 약 40건의 재검증이 발생했고 트레일링 슬래시 리다이렉트가 느린 폰에서 내비게이션당 약 800ms를 더했다. **LCP 요소였던 캐러셀 카드에 lazy-load가 걸려 있었다.** 화면 밖 히어로 애니메이션이 5초마다 메인 스레드를 약 446ms씩 쓰던 것도 오프스크린 일시정지로 고쳤다. 성능 예산을 팀과 AI 에이전트에게 함께 공유하라는 제안도 붙였다.
- [Node가 빠르려면 대부분 덜 하면 된다](https://www.thenodebook.com/blog/fast-nodejs-doing-less)와 [소프트웨어가 느린 건 언어가 아니라 설계 탓](https://seangoedecke.com/software-is-slow-because-of-bad-design-not-slow-languages/): 같은 이야기를 서버와 일반론 쪽에서 한다.
- [왜 개발자들은 플랫폼을 안 쓰나](https://nolanlawson.com/2026/10/03/why-dont-more-developers-use-the-platform/): Nolan Lawson의 자기반성. `<dialog>` 대신 `position: absolute`와 `z-index`로 모달을 직접 만드는 습관이 브라우저가 늦게 따라오던 시절의 잔재라고 본다. Hacker News에서는 네이티브 컨트롤이 실무엔 너무 제한적이라는 반박이 쏟아졌다. 같은 저자가 2주 뒤 쓴 [아무도 안 쓰는 웹 컴포넌트에 미래가 있나](https://nolanlawson.com/2026/10/19/do-web-components-have-a-future-if-nobody-is-writing-them/)와 묶어 읽으면 쓸쓸하다.

### 테스트와 안전장치

- [HTTP 복원력 라이브러리 11개를 테스트했다](https://blog.gaborkoos.com/posts/2026-10-04-I-Tested-11-Http-Resilience-Libraries/): ffetch 제작자가 Ky, ofetch, Wretch, fetch-retry 등 11개에 같은 21개 시나리오를 돌렸다. 147개 셀 중 통과 122, 실패 25. 기본 재시도는 전부 통과했지만 **대기 중에 다른 이벤트가 끼어드는 순간 대부분 무너졌다.** fetch-retry는 백오프 대기 중 abort 신호를 읽지 않아 취소 후에도 요청을 계속 보냈고(1회 기대, 실제 4회), wretch는 재시도 훅이 예외를 던지면 호출자 Promise가 영원히 settle되지 않았다. React Query나 SWR로 취소를 전파하는 앱이라면 지금 쓰는 fetch 래퍼가 백오프 중에 signal을 읽는지부터 확인해라. 시나리오가 ffetch가 고친 버그 기준이라 ffetch에 유리할 수 있다는 점은 저자도 인정한다.
- [Miro, 테스트 7만 개를 두 달 만에 Jest에서 Vitest로](https://nothing-else.blog/blog/we-migrated-70000-tests-from-jest-to-vitest-yes-in-2-months): 패키지 800개 모노레포를 AI 에이전트 중심으로 옮긴 경험담.
- [AI가 짠 코드 테스트하기](https://www.robinwieruch.de/testing-ai-generated-code/): Robin Wieruch는 컴포넌트마다 테스트를 붙이기보다 구조적 lint 규칙과 공용 하네스가 낫다고 주장한다. 패턴은 린트로, 결정은 테스트로.
- **AI가 만든 HTML을 격리된 미리보기로**: 모델이 쓴 HTML을 `srcdoc` iframe으로 렌더하면 내 origin에서 실행된다는 문제를 보안 엔지니어가 직접 깨 보이고 sandbox와 엄격한 CSP로 다시 쌓으며 장치 하나하나가 무엇을 막는지 보여 준다(Keshav Malik).

### 디자인 시스템과 에이전트

- [AI 에이전트를 위한 디자인 시스템](https://www.headway.io/blog/design-systems-for-ai-agents): 핵심 문장이 이번 달 전체를 요약한다. **강한 시스템은 AI 덕분에 더 빨라지고 약한 시스템은 더 빨리 엉망이 된다.** 사람은 애매하면 묻지만 에이전트는 애매함을 자신 있게 복제한다. 요건 다섯: 기계가 읽는 토큰(JSON, CSS 변수), prop과 state와 사용 맥락이 명시된 컴포넌트 문서, Figma와 코드 컴포넌트의 1:1 이름 일치, 리뷰 댓글 대신 lint 규칙에 박힌 조합 규칙, MCP 서버 같은 자동 전달 경로. 전담 owner가 없으면 다들 책임지는 척하다 아무도 안 한다는 경고도 붙었다.
- [새로운 진흙덩어리](https://www.nngroup.com/articles/big-ball-of-mud-ai/): NN/g가 에이전틱 시스템이 무너지는 다섯 패턴을 사용자 관찰로 정리했다. 임시 파일의 영구화, 단순 위젯이 예측 알고리즘까지 품은 대시보드로 자라는 점진 확장, 지운 파일을 휴지통에서 다시 꺼내 쓰는 억지 유지보수, 나중에 정리할 폴더가 너무 어질러져 AI가 엉뚱한 문서를 가져와 45분을 날린 사례, 결국 재구축. 처방은 컨텍스트를 전역, 로컬, 앰비언트 셋으로 나눠 섞지 말라는 것이다. `CLAUDE.md`나 `.cursorrules`를 전역과 태스크별로 쪼개는 데 그대로 쓸 수 있다.
- [코드가 더 이상 병목이 아닐 때, Anthropic 디자인팀](https://designerfund.com/blog/ai-design-anthropic): 2026년 5월 기준 머지된 코드의 80% 이상을 Claude가 썼고 엔지니어링 속도는 약 10배, 디자인 속도는 3\~5배가 됐다. 디자이너가 입사 첫 주에 PR을 올리고 `/fresh`, `/preview`, `/prototype` 같은 자체 워크플로 스킬을 쓴다. 크리틱은 주 2회 대규모에서 팟별 주 최대 4회 소규모로 바뀌었다. FE 쪽에서 가져갈 건 하나다. **디자이너가 로컬 서버를 직접 띄우는 환경이 전제라면 셋업을 스크립트 한 줄로 만드는 일이 프론트엔드의 몫이 된다.**
- [이름 짓기 실전 가이드](https://www.smashingmagazine.com/2026/10/how-name-things/): 토큰을 brand → primitives → semantics → page-level로 계층화한 보다폰 사례와 `blue-500` 같은 외형 이름을 semantic 토큰에 쓰지 말라는 원칙. 표준이라기보다 참고 자료 모음에 가깝다.
- **도구 넷**: [Caret](https://github.com/precious112/caret-desktop)(디자인 레이어를 저장소 안 `.caret/` 폴더의 실제 `.tsx`로 저장해 git으로 버전 관리하는 오픈소스 데스크톱 툴. 스타 30여 개의 초기 단계). [EditUI](https://www.editui.app/)(실행 중인 앱에서 요소를 찍어 수정 요청을 적으면 텍스트, DOM 클래스, computed style을 묶어 에이전트용 프롬프트 하나로 만들어 주는 크롬 확장. 콘텐츠 스크립트가 모든 페이지에 주입되니 권한 확인 필수). [Figma Specs](https://www.figma.com/blog/introducing-figma-specs/)(Figma, 팀, 에이전트가 공유 컨텍스트로 빌드하는 도구). [React DevTools for agents](https://react.dev/reference/dev-tools/react-devtools-cdt-mcp)(Chrome DevTools MCP로 코딩 에이전트에 프로파일링과 컴포넌트 데이터를 노출하는 공식 문서).

### AI를 쓴 사람들의 숫자

- [합성 사용자 대 실제 응답자](https://www.nngroup.com/articles/synthetic-users-vs-human-respondents/): NN/g가 AI 합성 응답자 120명과 실제 전문가 604명에게 같은 개방형 질문을 던졌다. 결론은 같았지만 사람은 50개 넘는 라벨을 쓴 반면 합성 쪽은 약 12개로 수렴했다. 합성 PM의 93%가 UX 용어를 썼고 실제 PM은 44%였다. 합성 사용자는 가설 생성용까지만.
- [UX 실무의 AI, 일은 빨라졌는데 기분은 복잡하다](https://www.nngroup.com/articles/ai-in-ux-survey-26/): 유효 응답 521명. 66%가 에이전트형 도구를 쓰고 시간 절감은 코드 작성과 디버깅에서 가장 컸다. 그런데 절약된 시간이 개인에게 남지 않고 더 높은 산출 기대치나 남의 AI 결과물 수정에 흡수된다. 직무 안정성 점수는 PM 3.81, 디자이너 2.99, 연구자 2.94. 자기선택 표본이라 대표성은 없다.

### 엔진과 브라우저

- [null 프로토타입 객체 최적화](https://adventures.nodeland.dev/archive/optimizing-objects-with-null-prototypes/): V8에서 `{ __proto__: null }`이나 `Object.create(null)`로 만든 객체는 처음부터 느린 dictionary mode로 시작한다. 평범한 객체를 만든 뒤 prototype을 null로 바꾸는 쪽이 더 빠르다는 걸 Matteo Collina가 보여 준다. 룩업 테이블을 많이 만드는 코드라면 한 번 재 볼 만하다.
- **JPEG XL이 모든 주요 브라우저에 들어갔다.** [Firefox 158](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/158)이 기본 활성화하면서다. Jake Archibald의 [AVIF와 비교한 긴 리뷰](https://jakearchibald.com/2026/jpeg-xl-vs-avif/)가 포맷 결정 전에 읽을 자료다.
- **Chrome 156**은 모듈 fetch 실패를 더 이상 캐시하지 않는다. 네트워크 오류로 실패한 동적 `import()`를 재시도할 수 있게 됐다. 청크 로드 실패에 새로고침 버튼만 띄우던 에러 바운더리를 다시 볼 이유다.
- [example.com은 왜 이제 JavaScript를 불러오나](https://www.oliverdunk.com/2026/09/30/iana-reply): 접속하는 클라이언트 대부분이 JS를 실행하지 않는 봇이라 대역폭을 아끼려고 그렇게 했다는 IANA의 답변.
